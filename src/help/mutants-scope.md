Which mutants `--mutants` runs, which survivors it holds, and what the gate holds without running any. Mutants run only on a change, and only those the agent picks: no command, flag or setting mutates the whole codebase or runs every mutant of a change, so a run's cost follows the picks, not the codebase's size.

- **The change** is what HEAD adds since its merge base with **the target**, the branch it lands on, untracked files included: `target` under `[check]` in `slimfit.toml`, or `origin/HEAD` (the remote's default branch) when unset. Code already on the target is never charged to a change; once a branch merges the target in, what it brought is out of the change. Nor is code from before this rule: when `.slimfit/baseline.json` sets `mutants_from` (a commit, set by hand once, when a codebase adopts the rule) and the target has not reached it, the change is taken from that commit instead. This page is where the term is defined; every other page means exactly this by it.
- **The changed lines** are its added source lines (neither blank nor only a `//` comment, outside inline tests), in the suites whose tool can list a change's mutants and run one by name ({const:DIFF_LIMITED}: the suite's `mutants_diff_flag`, `--in-diff`, and `mutants_pick_flag`, `-F`). For a suite whose tool cannot, `--mutants` refuses rather than run every mutant. With no target found, `--mutants` refuses, saying why.
- **The candidates**: `slimfit check --mutants` with no name lists the mutants of the files that hold changed lines, as the tool lists them from the change's diff, without building anything: each with its `name`, `file`, `line`, `function` and `replacement`.
- **The picks**: the agent reads its own change and picks at most {const:PICKS_MAX}, on the decisions the change makes: comparisons, boolean logic, match guards, a function whose return value matters. It skips the ones that cannot build, such as a body replaced by `Default::default()` for a type with no default: they are most of a listing, and each costs a build to learn nothing. `slimfit check --mutants <name>... --why <why>...` runs only those, each by its name, anchored; each `--why` is one line, in the order of the names. A name holds its line and column: after an edit above it, list again.
- {const:REACHED}: each mutant runs only the tests the test run saw run its function, each under a timeout of its own (see [costs](help:costs)). A test that never runs the mutated function cannot fail on it, so the verdicts are those of running every test. The test run records which functions each test ran (`reach_report`); a mutant whose function no test ran runs no test and, once it builds, is missed. When that is not known (no `reach_report` written, a `const fn`, a line in no listed function, a test whose profile could not be read), the mutant runs every test. `mutants_tests = "all"` in the suite runs every test on every mutant.
- A pick that survives fails `check` as `survived_mutants`, held at 0: each is the change's own. No baseline keeps a mutant count. One that changes nothing observable is accepted with `slimfit ratchet --loosen survived_mutants --reason "<why>"`.
- Surviving-mutant tasks come only from these runs: picks that survived, never the whole suite's.

The guarantee is the picks, not every mutant: a mutant nobody picked is not run, and its survival is not seen. A change that only deletes code or tests adds no line: it lists no mutant and needs no record, and what a deleted test killed in unchanged code is not seen. Likewise a change to a test file alone.

The output's `mutated` says, per suite, the `picks` it ran (each with `name`, `why` and `outcome`) and the picks by outcome (`change`).

## What the gate holds

A change that adds source lines reaches the target only with a record of its mutants. Mutants never run in a gate; the gate checks only that the change adds a record:

- A `slimfit ratchet` of a measurement that ran picks (and passed, or loosened its survivors with a reason) writes `.slimfit/mutants/<hash>.json`: the tree it was made of and, per suite, the picks, each with why and its outcome. `slimfit ratchet --no-mutants "<why>"`, when nothing in the change is worth a mutant, writes one with that reason instead, and no mutant runs. Nothing else writes one. Each is a file of its own, named by its contents (the tree among them), so two branches that each recorded their own change merge without a conflict.
- Every `slimfit check`, plain ones included, fails with `unrecorded_mutants` while the change adds source lines and no record (a `check --mutants <name>...` passes it: its `ratchet` writes the record). Which lines a record covers is not held: an edit after the record passes. Its `fix` is the rule: list, pick, run at background priority (`factorium worker exclusive --background -- slimfit check --mutants <name>... --why <why>...`; outside factorium, `nice -n 19 slimfit check ...`), then `slimfit ratchet`, or `slimfit ratchet --no-mutants "<why>"`; then commit `.slimfit/mutants/` with the change.
- `unrecorded_mutants` is never loosened: a record of none, with its reason, is the way past a change with nothing worth a mutant.
- `slimfit report` counts the records with picks against those without (`mutants_records`): a rule kept only in form shows there.
- With no target found, `check` holds nothing (its `landing` is `null`) and `slimfit doctor` finds `no_target`.

## Who runs it, and when

The agent that made a change lists its mutants, picks, and runs the picks at background priority (`nice -n 19`; in factorium, `factorium worker exclusive --background -- slimfit check --mutants <name>... --why <why>...`), then `slimfit ratchet`, then commits `.slimfit/` with the change. `slimfit next` asks for this first, as a `pick-mutants` task, when the change adds source lines and no record. Never in a gate: it would hold up every landing. Not as idle work either: idle work commits nothing, so what it runs is never recorded, and a red run is one nobody there can fix.
