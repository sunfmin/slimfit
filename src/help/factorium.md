How to place slimfit in a repo's gates, with factorium as the example.

1. `slimfit init` detects the suites, writes `slimfit.toml`, measures and writes `.slimfit/baseline.json`. Commit both. It runs no mutant.
2. In the gate, `slimfit check` runs in place of the project's own test run, never beside it. In factorium: `factorium.toml` has `fast = "slimfit check"`, or a gate script that calls `slimfit check`, with `cargo test` (or the language's test command) taken out of it.
3. Mutants go in no gate (`fast`, `slow`) and in no `[idle]` step: idle work runs in a throwaway clone and commits nothing, so what it runs is never recorded (the sample, below, records itself through an issue). The worker that made a change has a second agent pick the few mutants worth running, never itself (see [the picker](help:picker)): it runs `factorium worker pick-mutants`, which starts a fresh headless session on another harness of the kit (the worker's own as fallback), given only the goal (`slimfit help picker`), the diff and the candidates (`slimfit check --mutants`), and answers the picks, the picker's id (`harness:session:model`) and the commands that run and record them. The worker runs those commands: the picks at background priority, `factorium worker exclusive --background -- slimfit check --mutants <name>... --why <why>...` (see [mutants scope](help:mutants-scope)), then the `slimfit ratchet --picker <its id> --author <the worker's>` it answers.
4. When that passes, the worker runs `slimfit ratchet --picker <its id> --author <the worker's>`, which writes the change's record in `.slimfit/mutants/` (or `slimfit ratchet --no-mutants "<its why>" --picker <its id> --author <the worker's>` when the picker finds nothing worth a mutant), and commits it with the change. The gate's plain `slimfit check` fails on a change that adds source lines and no record naming a picker other than its author, so a landing cannot skip this step (see [what the gate holds](help:mutants-scope)). Workers' records are files of their own: merging proving into a branch brings them along, without a conflict.
5. An unbiased sample of what landed goes on `[idle]`'s tasks line, not in its steps: `tasks = "slimfit --version && slimfit next --all --sample 5"`. It runs a few mutants nobody picked, at the idle line's background priority; each sampled survivor is filed as a `surviving-mutant` issue and the sample's record as a `record-sample` issue, whose worker commits it, so `slimfit report` can set the sample's survival beside the picks' (see [the sample](help:sample)). No gate reads it.
6. What bounds a gate's time is its limit in the repo's `factorium.toml` (`fast_limit`, `slow_limit`), not slimfit: `test_seconds` moves with the host's load, so `slimfit check` shows it as a trend and never fails on it; `slow-test` tasks bring it down.
7. A change that adds more than `growth_allowance` source lines net (by default {const:GROWTH_ALLOWANCE}) carries a growth record (see [the reviewer](help:reviewer)): the worker cuts what it can, then has a second agent judge whether the change could be smaller, never itself: it runs `factorium worker review-growth`, which starts a fresh headless session on another harness of the kit (the worker's own as fallback), given only the goal (`slimfit help reviewer`) and the diff, and answers the verdict, the reviewer's id (`harness:session:model`) and the `slimfit ratchet` command that writes the record. The worker makes or answers the cuts the reviewer names, then runs the command it answers, `slimfit ratchet --serves "<the issue>" --considered "<what it weighed reusing or deleting>" --as-is "<its why>" --reviewer <its id> --author <the worker's>` (or `--cut "<what it named>" --answer "<what it did>"` in place of `--as-is`), filling in `--considered` and, for a cut, `--answer`, and commits `.slimfit/growth/` with the change. The gate's plain `slimfit check` fails without it (`unrecorded_growth`): a repo kept from bloating needs no line budget of its own in its gate.
8. The change is taken against `origin/HEAD`, the default branch proving is promoted to; set `[check] target` in `slimfit.toml` when changes land elsewhere.
9. A worker on a `redundant-test` task measures the whole suite once before its gate, in one order: change the tests -> run the changed file's tests with the project's own test command (plain, fast) -> its picks, as in 3 -> `slimfit ratchet` -> commit -> `factorium worker gate`. The gate's `slimfit check` verdict is the task's accept (no test fails, no `new_spans`, and after a merge `test_seconds` falls): the worker runs no separate `slimfit check` before it, which the gate would repeat, and ratchets before the gate, so the gate's tree is the one that lands.

Time it first: [costs](help:costs) says how. Then `slimfit doctor` names whatever in this placement is off, each with its fix.
