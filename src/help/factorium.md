How to place slimfit in a repo's gates, with factorium as the example.

1. `slimfit init` detects the suites, writes `slimfit.toml`, measures and writes `.slimfit/baseline.json`. Commit both. It runs no mutant.
2. In the gate, `slimfit check` runs in place of the project's own test run, never beside it. In factorium: `factorium.toml` has `fast = "slimfit check"`, or a gate script that calls `slimfit check`, with `cargo test` (or the language's test command) taken out of it.
3. Mutants go in no gate (`fast`, `slow`) and in no `[idle]` step: idle work runs in a throwaway clone and commits nothing, so what it runs is never recorded (the sample, below, records itself through an issue). The worker that made a change lists its mutants (`slimfit check --mutants`), picks the few worth running, and runs them at background priority: `factorium worker exclusive --background -- slimfit check --mutants <name>... --why <why>...` (see [mutants scope](help:mutants-scope)).
4. When that passes, the worker runs `slimfit ratchet`, which writes the change's record in `.slimfit/mutants/` (or `slimfit ratchet --no-mutants "<why>"` when nothing in it is worth a mutant), and commits it with the change. The gate's plain `slimfit check` fails on a change that adds source lines and no record, so a landing cannot skip this step (see [what the gate holds](help:mutants-scope)). Workers' records are files of their own: merging proving into a branch brings them along, without a conflict.
5. An unbiased sample of what landed goes on `[idle]`'s tasks line, not in its steps: `tasks = "slimfit --version && slimfit next --all --sample 5"`. It runs a few mutants nobody picked, at the idle line's background priority; each sampled survivor is filed as a `surviving-mutant` issue and the sample's record as a `record-sample` issue, whose worker commits it, so `slimfit report` can set the sample's survival beside the picks' (see [the sample](help:sample)). No gate reads it.
6. What bounds a gate's time is its limit in the repo's `factorium.toml` (`fast_limit`, `slow_limit`), not slimfit: `test_seconds` moves with the host's load, so `slimfit check` shows it as a trend and never fails on it; `slow-test` tasks bring it down.
7. The change is taken against `origin/HEAD`, the default branch proving is promoted to; set `[check] target` in `slimfit.toml` when changes land elsewhere.

Time it first: [costs](help:costs) says how. Then `slimfit doctor` names whatever in this placement is off, each with its fix.
