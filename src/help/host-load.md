On a busy host everything runs slower by the wall clock: a gate, a mutants run, each mutant's tests. `test_seconds` is CPU time (the `test_seconds` bound in `slimfit check --help` says what it counts), and waiting for a core does not add to it: the tests do the same work however long they wait. With every core busy it still rises a little (on Apple silicon more of the work lands on the slower cores), far less than wall time.

`slimfit doctor` finds `host_busy` when the 1-minute load average (`uptime`) is above {const:BUSY_LOAD} per core (cores: `sysctl -n hw.ncpu` on macOS, `nproc` on Linux). Wall times taken then run high: a gate's, the test command's (`command_seconds` per suite in `.slimfit/out/measurement.json`), and the costs [costs](help:costs) tells you to time.

## A test run inside `--mutants`

`slimfit check --mutants` runs at background priority (rule 2). On a host with fast and slow cores (Apple silicon) such a process runs on the slow ones, where the same work takes more CPU time. When it finds no cached test run of the tree it runs the tests itself, and that run's `test_seconds` is not what a gate measures: it holds the run's coverage, failures and which tests ran which function, but not its time. Its `check` answers the suite in `time_unchecked` and holds no `test_seconds` bound; `slimfit ratchet` keeps the baseline's `test_seconds` as it was, and refuses `--loosen test_seconds` and a suite with no baseline yet. A plain `slimfit check` of the same tree runs the tests again, at its own priority, and keeps the mutants: `test_seconds` is checked, and ratcheted, only from such a run.
