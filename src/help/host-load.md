On a busy host everything runs slower by the wall clock: a gate, a mutants run, each mutant's tests. `test_seconds` is CPU time (the `test_seconds` row in `slimfit check --help` says what it counts): waiting for a core does not add to it, but on a host with fast and slow cores (Apple silicon) more of the work lands on the slow ones under load, where the same work takes more CPU time. On one such host the same tree measured 12.0 s at a 1-minute load of 22, against the 8.8 s its baseline kept. So `test_seconds` is a trend and the source of `slow-test` tasks, not a bound: `slimfit check` answers it beside the baseline and never fails on it.

`slimfit doctor` finds `host_busy` when the 1-minute load average (`uptime`) is above {const:BUSY_LOAD} per core (cores: `sysctl -n hw.ncpu` on macOS, `nproc` on Linux). Wall times taken then run high: a gate's, the test command's (`command_seconds` per suite in `.slimfit/out/measurement.json`), and the costs [costs](help:costs) tells you to time.

## A test run inside `--mutants`

`slimfit check --mutants` runs at background priority (rule 2). On a host with fast and slow cores (Apple silicon) such a process runs on the slow ones, where the same work takes more CPU time. It reuses a test run of the same files at a gate's priority, kept in `.slimfit/out/` whatever HEAD is: a gate's run before you commit the change counts. When it finds none it runs the tests itself, and that run's `test_seconds` is not what a gate measures: it holds the run's coverage, failures and which tests ran which function, but not its time. Its `check` answers the suite in `time_unchecked`, not in `test_seconds`. `slimfit ratchet` then times the tests again, at its own priority, keeping the mutants, as a plain `slimfit check` of the same tree does: `test_seconds` is answered, ratcheted and kept in the baseline's `measured` only from such a run. A `measured` with no `test_seconds` says why in `untimed`; one from before baselines said so dropped the time unsaid.
